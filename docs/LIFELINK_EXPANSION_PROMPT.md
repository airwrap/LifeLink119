# Codex 실행 프롬프트 — LifeLink 119 통합 확장 및 초간편 UX 리팩터링

> **사용법:** 이 파일을 기존 LifeLink119 프로젝트 루트에 `docs/LIFELINK_EXPANSION_PROMPT.md`로 복사하거나, 아래 내용을 VS Code의 Codex 채팅에 그대로 붙여넣으세요. **새 프로젝트를 만들지 말고 현재 구현된 코드에 적용**하게 하는 프롬프트입니다.
>
> **프로젝트:** 현대차·기아 Pleos Connect 앱 공모전용 LifeLink 119. 사용자 가치: “내 차가 나와 내 가족을 위한 응급지원 공간으로 변신한다.”

## 0. 너의 역할과 최상위 목표

너는 Android Automotive OS(AAOS), Kotlin, Pleos Connect SDK, 접근성(a11y), 응급지원 서비스 UX, 테스트 자동화 전문가로 구성된 시니어 개발팀이다. **현재 열려 있는 기존 저장소를 먼저 조사**하고 기존에 정상 동작하는 것을 유지하면서 제품 수준의 인터랙티브 공모전 데모를 구현하라.

**제품 원칙: 기능 100% 시연, 첫 화면의 복잡성 최소화.** 이전에 기획한 기능과 14가지 응급 시나리오를 모두 사용자가 체험할 수 있게 구현하되, 모든 기능을 홈 화면에 일렬로 나열하지 않는다. 기능의 실구현/시뮬레이션/제휴 필요 여부는 화면 및 문서에서 정직하게 구분한다.

**작업 방식:** 이 프롬프트는 설계 조언만 요청하는 것이 아니다. 가능한 범위에서 **실제 파일 수정, 실행 가능한 코드 작성, 테스트와 문서 업데이트**까지 수행하라. 처음부터 새 Android 프로젝트 생성, 기존 UI 전면 삭제, 구조가 다르다는 이유로 작성 중단하는 행동은 금지한다. 한 번에 모든 작업이 어렵다면 구현·테스트가 가능한 작은 단계로 나누어 **순서대로 실행**하고, 마지막에 완료/미완료 항목을 정확히 보고하라. 별도 요청 없이 로컬 Git 커밋·푸시, 계정연결, 실제 긴급신고, 외부로 개인정보 업로드는 하지 마라.

## 1. 저장소 조사와 구현 규칙

1. 현재 저장소의 `README.md`, `AGENTS.md`, `settings.gradle.kts`, `app/build.gradle.kts`, `AndroidManifest.xml`, 핵심 Activity/Fragment/Compose/XML, `core`, `data`, `vehicle`, `test` 등을 실제로 읽는다. `AGENTS.md`의 규칙을 우선 적용한다.
2. 현재 패키지명·Gradle·Kotlin 버전·UI 프레임워크(Compose/Views)·테스트 프레임워크·SDK 의존성·앱 ID를 파악한다. **기존 스택을 유지**하며 UI를 점진적으로 리팩터링한다. Compose가 없으면 무조건 추가하지 말고 기존 Views로도 품질 높은 UI를 구현해도 된다.
3. 기존 `MainActivity`, `PleosVehicleGateway`, `CameraGateway`, `MockDispatchGateway`, `EmergencyScenario`, `FlowPolicy` 등 유사 구현이 있으면 재사용·변경하고 중복 클래스를 만들지 않는다. 이미 구현된 실제 기능은 버리지 않는다.
4. 기존 기능 목록과 현재 구현 상태를 `docs/FEATURE_AUDIT.md`에 기록한다. 이후 새로운 기능을 추가한다.
5. AAOS/Pleos Connect Emulator에서 동작 가능한 앱 유지. 기본 환경: Android SDK API 34, `minSdk >= 28`. 실제 사용 중인 프로젝트 설정이 이 조건을 충족하면 불필요하게 변경하지 않는다.
6. SDK API·퍼미션은 코드/공식 문서/에뮬레이터에서 확인된 것만 사용한다. 확인되지 않은 메서드를 추정해서 호출하지 않는다. SDK 의존성이 해결되지 않으면 인터페이스+Mock 구현으로 컴파일 경로를 유지한다.
7. 기존 에뮬레이터 실행 및 Vehicle SDK 진단은 계속 가능해야 한다. 차량 SDK 콜백, lifecycle의 `initialize()`/`release()`, 권한 오류, 미지원 capability를 처리한다.

## 2. UX 설계 철학 — 기능이 아니라 사용자 의도 중심

절대 하지 말 것: 첫 화면에 `119 의료상담 / 119 영상 / 112 / 109 / 카메라 / 가족 / 길찾기 / EV / V2L / 119안심콜 / AI / 수어 / 프로필...` 같은 버튼을 격자로 깔기. 홈에서 기능명/시스템 용어를 모르는 사람도 이해하게 할 것.

### 첫 화면(홈): 의미 있는 주 행동 2개 + 보조 정보 1개

- 상단: 브랜드 `LifeLink`, 짧은 문장 **“어떤 도움이 필요하세요?”**
- 최우선 큰 CTA: **`지금 긴급해요`**. 대체 텍스트: “119 구조·구급 / 112 긴급신고”. 도달 후 `119 연결`과 `112 연결`의 큰 선택, 늦지 않도록 어떤 프로필·등록·상담 문답도 요구하지 않음. 시연에서는 실제 번호로 연결되지 않으며 항상 `연결 시연`을 명확하게 표시.
- 두 번째 큰 CTA: **`상담받고 싶어요`**. `119 응급의료상담`, `109 심리위기 상담`을 보여줌. 응급 증상을 호소하거나 위험이 임박한 경우에는 119 긴급신고로 빠르게 이동할 수 있는 경로를 제공하되 AI가 임상적 중증도 판정하지 않음.
- 아래 작은 보조 진입점: **`우리 가족 응급정보`**. 평소 프로필 편집 및 장애 접근성 설정. 로그인/프로필 등록이 긴급 연결의 전제조건이 아니어야 함.
- `차량 안전 준비`(EV·V2L·차량정보), `설정·시연 도구`는 작은 보조 메뉴/더보기 내부. 숨겨두되 찾아갈 수 있게 표시하고 평상시 첫 화면을 어지럽히지 않는다.
- 어느 화면에서든 `홈`으로 복귀할 방법과 긴급경로(119/112)로 빠르게 이동할 수 있는 방법을 제공하되, 플랫폼 주행 규제를 우회하지 않는다.

### 정보 노출의 4단계(Progressive Disclosure)

1. **의도**: `지금 긴급해요` / `상담받고 싶어요`만 먼저 선택.
2. **기관**: `119` / `112` / `109` 중 상황에 맞는 경로로 이동. 긴급 경로는 깊은 분기 없이 직접 진입. 필요시 사용자가 다른 기관으로 전환 가능.
3. **개인화**: 선택적 `누가 도움이 필요한가요?`와 `어떤 도움이 필요한가요?`는 **연결 요청 이후**에도 수정 가능. 증상 목록을 강제하지 않고 `건너뛰기` 제공.
4. **연결 후 맥락형 행동**: 그 상황에 의미 있는 최대 **3개 기본 작업**만 표시. 추가 기능은 `추가 지원` 아래에 모은다. 예: 어린이 → `응급정보 공유`, `영상 보여주기`, `위치 전송`; 사고 → `차량 위치`, `현장 영상`, `이송·경찰 협조`; 청각장애 → `문자로 설명`, `수어통역`, `위치 공유`.

### 무조건 지킬 사용성 원칙

- 홈 화면의 대표 행동은 최대 2개. 긴급 신고 경로는 **프로필 설정 없이 즉시** 도달.
- 각 화면에는 주 CTA 1개, 보조 행동은 최대 2개를 우선 노출. 나머지는 맥락형 더보기.
- 의미 없는 단계/확인창을 줄이되, 민감정보 제공 전 동의는 생략하지 않음. **동의 없이도 신고 경로 사용 가능**.
- `상담 연결 시연` / `가상 소방상황실` / `실제 신고 아님`을 항상 정확히 표시. 연결되지 않았는데 ‘연결 완료’, 경찰 협조가 승인되지 않았는데 ‘에스코트 확정’이라고 표시하지 말 것.
- 앱을 처음 본 고령자·어린이 보호자·장애인도 버튼 라벨만으로 행동을 이해할 수 있도록 문장을 쓰고, 영어·전문약어·불필요한 아이콘을 줄인다.
- 주행 중에는 긴 텍스트 입력/리스트 스크롤/영상 표시 등 규제 대상 기능을 숨기거나 비활성화하며 안전한 정차를 권고한다. **CarUxRestrictionsManager 상태와 ActiveRestrictions를 준수**. DO 허가/카테고리 승인 없이 주행 중 인터랙티브 기능이 허용된다고 가정하지 말 것. 긴급 접근은 OEM/플랫폼이 허용한 범위에서만 제공하며, 불가하면 OS 표준 긴급통화 경로 안내/핸즈프리 대안을 검토할 것.
- 큰 탭 영역(최소 48dp; 차량 환경에서는 충분히 크게, 실제 Pleos UI 기준 확인), 가독성 좋은 기본 글씨, 고대비, 큰 글씨, 스크린리더 `contentDescription`, 포커스 순서, 명확한 선택 상태. 색상만으로 긴급도를 구분하지 않는다.
- 화면 방향과 윈도 크기에 대응(landscape/portrait), 에뮬레이터 화면에서 짤림·버튼 겹침·극단적 스크롤이 없도록 검증.

## 3. 사용자에게 보이는 최소 화면 구조

네비게이션은 아래의 단순 계층을 지향하고 중복 페이지를 제거한다.

```text
[HOME]
  ├─ [긴급해요] ─── [119/112 빠른 선택] ──────┐
  ├─ [상담받고 싶어요] ─── [119 의료/109] ────┤
  ├─ [우리 가족 응급정보] ─── [프로필 목록/편집]
  └─ [더보기] ─── [차량안전·EV 준비/시연 도구/설정]
                                             ↓
                                   [응급지원 세션]
                                   - 가상 연결 상태
                                   - 개인별 상황 카드
                                   - 지금 필요한 2~3개 행동
                                   - 추가지원(영상·위치·이송·경찰 등)
                                             ↓
                                   [종료/요약/개인정보 정리]
```

- 홈에 5개 탭·사이드바·복잡한 기능 대시보드 금지.
- 프로필에 따라 **연결 이후** 우선 버튼만 달라진다. 자녀/고령자/청각장애/시각장애/이동장애/임산부 등의 대체 레이아웃을 UI 컨텍스트로 반영한다.
- `모든 기능 보기`는 일반 사용자에게 노출시키지 말고 **더보기 > 시연 도구 > 시나리오 갤러리**에 넣는다. 심사위원이 14개를 빠르게 테스트할 수 있도록 표본 데이터와 1클릭 실행 제공.
- `연결 시연`은 모의 세션 생성 및 mock 상담원/상황실 화면 표시까지 **실제 동작**해야 함. 클릭만 되고 아무 변화 없는 장식 버튼 금지.
- 119/112/109 모의 연결 화면은 기관별 기능과 문구가 정확히 다르게 나타나야 함. 112는 범죄·폭력·교통통제 등, 109는 전문 심리상담, 119는 구조·구급·의료상담 역할 구분.

## 4. 14개 상황의 100% 체험 구현 — 유사 화면 재사용 + 다른 데이터와 행동

시나리오 기반 엔진(`ScenarioCatalog`, `RecommendationRules` 등)의 **선언적 데이터**로 구성하라. 14개마다 별도 Activity를 복제하지 않는다. 각각 선택 → 맥락 카드 → 모의 연결 → 우선 행동 → 세션 완료 흐름이 존재하고 테스트 가능한 fixture를 갖춰야 한다.

|---|---|---|---|
| S01 | 어린이 호흡곤란 | 119 긴급 | 아이 프로필·알레르기·영상상담 안내 |
| S02 | 심한 알레르기 반응 의심 | 119 긴급 | 처방·알레르기 정보 카드·보호자 |
| S03 | 고령자 의식 저하/뇌졸중 의심 | 119 긴급 | 증상 발견시각 기록·병력·위치 |
| S04 | 심장질환자의 흉통 | 119 긴급 | 기저질환·복용약·정보 동의 |
| S05 | 당뇨병 환자의 의식 변화 | 119 긴급 | 혈당 측정값(사용자 입력시)·병력 공유 |
| S06 | 발작 발생 | 119 긴급 | 시작 시각·관찰사항·응급지도 연결 |

| S13 | 심리위기·폭력 위협 | 109 또는 112/119 | 프라이버시·전문기관 전환·보호자 자동 알림 금지 |
| S14 | 교통사고·차량 고립 | 119/112 | 외부 영상·차량정보·공동대응·구급대 만남 장소 |

시나리오의 구체적인 의료 안내문에는 사용자가 임의 처치하도록 만드는 처방·진단·독자적인 중증도 결정 등을 넣지 마라. **위험 징후 시에는 전문가 연결 우선** 문구를 제공한다. 시연 중 실제 전화 발신 없음.

위 표 외에 `E01 전기차 정전/V2L`, `E02 자가용 환자 이송과 112 협조`, `E03 어린이·고령 부모와 함께 탑승`, `E04 일반 미등록 승객` 등 자동차 고유 시나리오도 갤러리에 추가한다. 14가지 응급상황을 빠짐없이 제공하면서 E01~E04의 기능 시연도 완성하라.

## 5. 반드시 구현할 기능 — 지원 불가해도 상호작용 가능한 데모 제공

**아래 A~M 모두 UI와 동작 경로를 제공**해야 한다. 실제 외부 시스템 연동이 불가하면 단순 ‘준비 중’ 문구만 쓰지 말고, 인터페이스를 분리하여 **Mock Gateway + 현실적인 상태 전이 + fixture 데이터 + 결과 화면**을 구현한다. 단, 실제처럼 보이도록 오해하게 하는 데모는 금지.

### A. Family Safety Profile
- 가족 등록/편집/삭제, 닉네임·연령대·보호자 연락(가짜 예시), 기저질환/복용약/알레르기/임신 관련 참고정보, 긴급 시 참고사항.
- 장애별 접근성 선호(청각/언어/시각/인지/이동), 큰 글씨·텍스트 모드·쉬운 안내.
- 가족 구성원 선택은 선택적. **미등록 사용자로 응급 경로 전체 실행 가능**.
- 처음에는 `김하늘(어린이/알레르기)`, `박민수(고령자/심장질환)`, `이지은(청각장애)`, `일반 승객` 등 명백한 가상 프로필을 seeded fixture로 제공(실존 개인정보 금지).
- 의료정보를 차량 이용자 전체가 무조건 볼 수 없도록 잠금/재확인 UI 및 민감정보 마스킹. 공모전 앱에서는 가상정보만 저장하는 demo mode 기본.

### B. Emergency Card 및 선택적 동의
- 이름 또는 별명·선택 의료정보·접근성·보호자·차량 위치/정보를 최소 화면에 요약.
- ‘의료정보 공유’는 항목별 승인/거절/취소(필요에 따라 전체 선택 가능)와 전송 대상/시연 여부를 명확히 보여준다. **동의 거절해도 신고 가능**.
- 공유 결과는 외부 서버가 아니라 가상 상황실 fixture에 반영. 세션 종료 시 메모리에서 민감한 데이터를 정리할 수 있게 설계.

### C. 119 의료상담 및 긴급신고, 112, 109
- 응급상담(119)과 긴급신고(119)는 목적이 다르므로 각각 표현.
- 112는 폭력/범죄 및 공동대응 모의 요청. 경찰 에스코트는 `요청됨 → 검토 중 → 가상 승인/거절` 단계로만 시뮬레이션; **자동으로 에스코트 권리/교통법규 특례가 생긴다고 안내하지 말 것**.
- 109 전문 상담 시뮬레이션은 사용자 프라이버시 보호, 119/112로 빠른 전환을 제공. AI 자살위험 추론, 가족 자동 통보 금지.
- `CallGateway` 등을 추상화하고 데모 빌드에서는 **전화 Intent, tel:112/119/109, 문자발송, 웹훅 등 실제 긴급 연락 동작을 완전히 차단**. 시연 상태/요청 내용을 앱 안의 가상 상담센터에서만 표시.
- 차후 실서비스는 OEM/소방·경찰/공식 신고 인프라 권한과 인증 후 별도 flavor에서만 고려; 현재는 의도적으로 구현하지 않음.

### D. 가상 상황실(모의 센터)
- 차량 앱 안에서 상담원 뷰(전환 가능한 화면/패널) 제공. PC 브라우저용 데모 서버가 이미 있으면 재사용, 없으면 앱 내 상담원 카드만으로도 전체 시연이 끝나게 구성.
- 기관(119/112/109), 연결상태, 사용자의 증상 설명, 선택 가족정보, 동의한 위치/차량정보, 영상 유무, 공동대응 요청상태 등이 갱신되는 것을 보여준다.
- `연결 요청 → 연결 중 → 가상 상담원 응답 → 정보 공유 → 안내 → 종료` 등의 명확한 state machine.
- 통신 장애, 위치 없음, SDK 미지원, 동의 거절, 보호자 정보 미등록 상태도 사용자에게 설명 가능해야 함.

### E. Video Gateway 및 빌트인 캠 확장
- 차량 외부 영상: 시연 자산 또는 가상 feed(보안상 안전한 샘플), `카메라 공유 요청 → 승인 → 공유 중(DEMO) → 종료`, 전·후방 소스 선택 UI. 실제 빌트인 캠 API가 없음/불명확하면 `BuiltInCamGateway`는 MOCK으로 명시.
- 차량 내부 환자 영상: 스마트폰/보조 카메라 연계의 **모의 UI 및 영상 소스** 제공. 본인/환자 동의·영상 사용범위 고지.
- 주행 제한 감지시 차량 디스플레이에서 동영상 재생·미리보기 차단. 공유 여부와 `영상 전송 중(시연)`을 혼동하지 않게 화면 명시.
- 비공식 빌트인캠 우회 접근, 파일 무단 읽기, 카메라 상시 녹화 금지.

### F. 위치·차량정보·Pleos Vehicle SDK
- 기존 작동하는 SDK 연동 유지, 허용된 차량 상태(차량 기본정보·EV SOC/충전상태 등)만 최소 권한으로 조회.
- 실제 위치 API 사용권한이 없으면 `MockLocationGateway`로 명백한 가상 좌표/지역을 표시; **실제 위치라고 주장하지 않음**.
- 권한 거절/SDK 오류/비전기차/미지원 차종 등에서 graceful fallback 제공.
- `data source: REAL / MOCK / NOT_AVAILABLE` 상태를 시연 도구와 관련 화면의 보조 문구에서 표현.

### G. Navigation Gateway
- `NaviHelper` 지원 확인 후 목적지/경유지 설정 및 상태 피드백 구현. 불가하면 모의 내비게이션으로 `경로 제안 → 사용자가 확인 → 시연 목적지 설정 완료` 흐름 표시.
- 선택 가능한 목적지는 가상 병원/구급대 만남 장소 등 fixture. 앱이 의료기관 수용 가능 여부를 판단·보증하면 안 됨.
- 병원 이동은 **119/전문가 안내에 따르는 경우에만** 지원; 무조건 자가용 자가 이송 유도 금지.

### H. 112 공동대응 및 교통 지원
- 긴급신고 연결 화면에서 `경찰 협조 요청` 진입 가능. 담당기관이 승인/거절을 결정하는 가상 상태 전이 구현.
- 실제 112 공동대응의 자동 연계/경찰 출동/도로 우선통행 권한을 보장하거나 사칭하지 않는다.
- 112 직접 신고가 필요한 상황에는 119 절차를 강제하지 않는다.

### I. 119안심콜 연계 콘셉트
- `119안심콜 등록 여부` 및 등록된 전화번호 확인 도움말, LifeLink 정보 연계 동의 카드, `모의 안심콜 정보 조회` 시연 구현.
- 공식 인증/기관 협약 없이 실제 119안심콜 조회 API가 있다고 가정하지 말 것. 앱이 프로필을 선택했다고 실제 상황실로 정보가 전달된다는 표현 금지.

### J. 차량 기반 접근성
- 청각/언어장애: 문자 중심, 대형 정형 문구 버튼, 수어통역 연결 안내/모의 3자 영상 UI.
- 시각장애: 스크린리더 구조·명확한 읽기 순서·음성 도움말(실제 권한 없는 경우 로컬 Android TTS 검토 또는 녹음 없는 mock).
- 인지장애: 전문용어 없는 단계별 짧은 문장, 보호자 도움 선택·선택 취소 가능.
- 이동장애: 휠체어, 보조기기, 승하차 도움이 필요하다는 정보 전달.
- 설정은 강제하지 않고 세션 시작 후에도 바꿀 수 있다.

### K. AI 상담 보조(안전한 범위)
- 규칙 기반/템플릿으로 `언제·어디서·누가·무슨 상황·어떤 도움을 원하는가`를 **사용자가 검토·수정 가능한 형태로** 요약한다.
- 앱에서 의료진처럼 진단, 투약 결정, 자살위험 자동평가, 경찰/병원 배치 결정을 하지 않는다. `AI가 판단했다`라는 표현보다는 `상담 전달용 정보 요약`으로 표기.
- 추후 LLM 연결은 추상화 인터페이스만 두며 기본 공모전 빌드는 완전 오프라인으로 실행되게 할 것.

### L. EV Emergency Power / V2L
- 전기차 여부/SOC/배터리 용량 입력(또는 SDK 지원 시 조회), 보존 SOC, 전력기기 소비전력(사용자 입력), 변환 효율을 이용해 **가정이 표시되는** 사용 가능 전력량/예상 시간 계산.
- 예시 수식: 사용가능량(kWh)=배터리용량(kWh)×max(0,현SOC−보존SOC)/100×효율; 시간(h)=사용가능량(kWh)/(부하W/1000).
- V2L 지원 여부/출력 제한은 차종·사양 확인 필요, 비지원 차량은 별도 안내. 의료·생명유지장치의 안전한 전원 공급을 보장하지 않는다.
- 차량 제어 SDK가 지원되지 않는 상태에서 실제 V2L·비상등·도어·공조를 작동시키지 않음.

### M. 차량 프로필·디지털 키 연계 콘셉트
- `운전자 프로필 자동 선택`을 가상 시나리오로 시연(디지털 키 등 실제 OEM API 연동은 현재 확인된 경우만).
- **운전자 인식과 동승자 식별은 별개**: 동승자는 반드시 선택/동의를 통해 지정. 감시형 탑승자 인식이나 민감정보 무단 노출 금지.

## 6. 도메인 모델과 아키텍처(현재 구조에 맞게 이름 조정 가능)

중복 Activity/Fragment를 만드는 대신 단일 화면 흐름과 공통 컴포넌트를 사용하라.

```text
ui/
  home/                  # 두 개의 큰 주 CTA
  entry/                 # 기관 선택 119/112/109, 안전한 긴급 연결
  session/               # 상황별 우선 동작 2~3개, 추가 지원
  profile/               # Family Safety Profile / Emergency Card
  demo/                  # 14+4 시나리오 갤러리, 가상 상황실
  vehicle/               # EV/V2L, 차량 연동 상태
  components/            # 큰 CTA, 상태표시, 확인, 접근성

domain/
  model/                 # PersonProfile, MedicalNotes, AccessPreferences,
                         # EmergencyScenario, EmergencySession, ShareConsent,
                         # LinkStatus, ConnectionTarget, CapabilityStatus
  engine/                # ContextualActionResolver, SessionStateMachine
  usecase/               # StartSession, SelectPerson, ShareCard, SimulateContact,
                         # UpdateCase, RequestAssistance, EndSession

data/
  repository/            # Secure/Fake Profile, Scenario fixtures, Session
  gateway/               # EmergencyCall, Dispatch, Camera, Vehicle, Location,
                         # Navigation, PoliceAssist, SafePower, Speech
  mock/                  # 시연 중 전 네트워크·기관 동작의 결정론적 Mock
  pleos/                 # 확인된 실제 SDK 어댑터만

docs/
  UX_SPEC.md
  FEATURE_MATRIX.md
  DEMO_SCRIPT.md
  SDK_GAPS.md
  IMPLEMENTATION_REPORT.md
```

- 단일 진실 공급원(상태): `EmergencySession` 모델로 `IDLE → REQUESTING → DEMO_CONNECTED → SUPPORT_IN_PROGRESS → COMPLETED/CANCELLED` 등 세션 상태를 일관 관리. 재진입/화면 회전/프로세스 재생성에서 상태 손실 최소화.
- `ContextualActionResolver(profile, scenario, connectionTarget, capabilities, drivingRestrictions)`가 노출할 **기본 행동 최대 3개**와 추가 행동을 결정. 이유 없는 AI 블랙박스 추천 금지.
- `CapabilityStatus = REAL | MOCK | NOT_AVAILABLE | NEEDS_PARTNERSHIP` 같은 소스 구분을 명확히 관리.
- 기능 인터페이스는 기존과 동일 기능이면 **중복하지 말고 통합**한다.
- profile의 민감정보는 기본적으로 fixtures만 사용, 실제 사용자 데이터를 넣게 되면 Android Keystore 기반 암호화 및 접근 제어/삭제 등 설계를 구현하거나 명확히 비활성화. Logcat, 크래시로그, Analytics 등에 병력/연락처/영상정보 저장 금지.
- 로컬 전용 데모가 네트워크/카메라 권한 없이도 끝까지 동작해야 함. 권한 있는 SDK를 선택적으로 연동할 수 있는 구조.

## 7. 구체적인 시연 흐름(심사 2~3분용)

**A. 어린이 응급상황(주 시나리오)**
1. 홈의 `지금 긴급해요` 선택 → `119 연결 시연` (2단계 이내, 프로필 미선택 가능).
2. 모의 센터 연결 후 `누가 도움이 필요한가요?` → `하늘(어린이)` 선택.
3. 상황 선택 `호흡곤란` → `응급정보 카드` 자동 요약(수정 가능).
4. 동의 화면에서 병력·알레르기만 공유 선택 → 가상 상황실에 정확히 그 정보만 표시.
5. 스마트폰 카메라 모의 영상 연결 → 시연 영상 공유/중단 → 위치 공유 → 상담원 안내 결과 표시.
6. 상담 세션 종료 → 데이터 정리 안내.

**B. 청각장애인 신고(접근성 차별화)**
1. 시연 갤러리에서 S08 선택 → 문자/수어 우선 UI 확인.
2. 프리셋 문구 `사고가 났어요 / 말을 할 수 없어요`를 선택 → 문자 신고 모의 요약.
3. 수어통역 모의 연결·현장 영상/위치 공유 체험.

**C. 교통사고 + 112 협조(현대차 특화 비전)**
1. S14 선택 → 가상 외부 전·후방 카메라 영상의 `공유 요청 → 공유 중 → 중지`.
2. 차량 위치 및 상태를 가상 센터에 전송(모의).
3. `112 공동대응 요청` → `검토 중` → 시연 승인/거절 선택. **경찰 에스코트 보장/긴급자동차 권한 주장 금지**.
4. 전문가가 지정한 가상 만남 장소를 내비게이션에 설정하는 단계 시연.

**D. EV 안전 기능(추가 20초)**
- 더보기 > 차량 안전 준비에서 SOC와 V2L 계산기를 실시간으로 조작하고 계산 결과 변경 확인. 비지원/안전 유의 문구 확인.

## 8. 반드시 구현할 상태·오류·보안 규칙

- 앱은 시연 환경에서 전화·문자·긴급기관 API 실제 호출을 하지 않는다. 테스트도 실제 번호로 요청 금지.
- 안내 문구 예: `실제 119 신고가 아닙니다`, `가상 상담원과 연결된 상태입니다`, `영상 공유 중 — 시연`, `경찰 협조 요청 — 모의 검토 중`.
- `앱 연결 실패/인터넷 없음/SDK 미지원/권한 거절/위치 없음/프로필 없음/상담 대상 변경/동의 취소/영상 공유 중단`에서 앱이 종료되지 않고 명확히 복귀.
- 기기 화면이 다른 앱으로 전환될 때 영상미리보기와 민감정보를 적절히 숨김. 기록 재조회 및 세션 정리는 분리.
- 상황에 상관없이 중요한 조작이 너무 깊게 숨지 않도록 검증(긴급 경로 ≤2 탭의 **시연 진입 목표**, 단 플랫폼이 허용하는 범위에서만).
- 장애 설정은 우선순위·표시방식 조정이지 특정 기능의 접근 자체를 차단하는 조건이 아님.
- 피싱/사칭/실제 신고 오인 방지용 `DEMO` 라벨, 더미센터/더미 환자 표시, 안전 확인/취소 버튼을 구현.
- 데이터 공유 완료와 동의 UI는 항상 실제 시뮬레이터의 전송 상태와 일치.
- `119안심콜 연계`, `빌트인캠 실시간`, `경찰 공동대응`, `차량 프로필 자동 인식`, `FusedLocation/STT/TTS` 등 미확인 기능은 실제 구현 주장 금지.

## 11. Codex에 대한 최종 실행 지시

**지금부터 조언만 작성하지 말고 기존 저장소를 실제로 조사한 다음 코드 수정에 착수하라.** 가장 먼저 기능 감사와 빌드 기준선을 확인하고, 다음에 심플한 홈 UX와 세션 흐름부터 구축한 뒤 모든 시나리오를 data-driven 방식으로 추가하라. 기존 완성된 기능을 손상시키지 않고 모든 Mock이 사용자에게 동작으로 관찰 가능하도록 만들어라.

결과 보고는 다음 양식으로 짧고 명확하게 출력하라.

1. `완료`: 구현된 기능 요약 + 대표 실행 경로
2. `변경 파일`: 핵심 파일 목록
3. `검증`: 빌드/테스트 통과·실패와 원인
4. `실제 vs Mock`: 기능별 기술적 사실과 미확인 사항
5. `다음 조치`: 에뮬레이터에서 확인할 항목/협력 필요 항목

**성공 기준은 버튼 수가 아니라, 프로필 없는 초보 사용자도 긴급한 상황에서 헤매지 않고 전문 도움 경로를 찾고, 심사위원은 숨겨진 시연 도구로 모든 기능이 서로 연계된 모습을 체험할 수 있는가이다.**
