# 설명회 요구사항 대조와 차량 데이터 개선 · v0.16

> 후속 v0.16.1에서 공식 Console 입력과 설치 앱의 도어·SoC SDK 반환값을 비교해 일치를 확인했습니다. 에어백은 현 이미지 미지원입니다. [최신 SDK 검증 결과](SDK_RUNTIME_VERIFICATION_V16.md).

검토일: 2026-11-07. 대상은 제공받은 「현대자동차그룹 차량용 앱 개발 공모전 통합 온라인 설명회.txt」 전체 645줄과 현재 Kotlin/Android 소스다. 아래 시간은 해당 녹취의 재생 위치다. 행정 일정·심사 운영은 녹취 당시 설명이며, 최신 공고를 대체하지 않는다.

## 핵심 진단

LifeLink 119는 가족 건강정보 보호와 긴급 요청의 흐름을 갖췄지만, 차량 데이터가 핵심 경험에 연결되지 않았다. `PleosVehicleGateway`에서 운전석 도어·배터리를 실제 SDK로 읽더라도 별도 진단 화면에만 표시했다. 긴급 요청의 `ShareField.VEHICLE`은 고정 예시 SOC 72%, EV 계산은 수동 기본값 72%여서 실제 차량 값이 바뀌어도 이용 흐름은 그대로였다.

설명회의 요구는 SDK 개수 늘리기가 아니다. **차량에서 얻은 정보가 어떤 문제를 해결하고 앱의 어떤 행동을 바꾸는지**를 보여주는 것이다. v0.16은 이를 `차량 조회 → 출처·수신 시각 확인 → 명시적 동의 → 앱 내 상황실 전달`과 `조회한 SoC → EV 계산 입력`으로 연결한다. 실제 119·112 발신이나 기관 데이터 전송은 포함하지 않는다.

## 구현한 데이터 흐름

```text
사용자가 ‘차량에서 새로 조회’ 선택 (또는 이 화면에서 5초 확인 선택)
  → PleosVehicleGateway (기존 단일 worker / capability / 권한 / 15초 timeout)
  → 도어, SoC, 에어백 각각 성공·실패와 typed 값
  → VehicleContextController (포그라운드 / 화면 가시성 / 세대 확인)
  → VehicleSample (출처 + 수신 시각 + 값/범위)
      ├─ 사용자 동의 → SessionEngine.vehicleContextShare → 앱 내 상황실 수신
      │                 철회 / 만료 / 배경 전환 / 인물·세션 변경 / 종료 시 삭제
      └─ 사용자 ‘SoC 불러오기’ → EV 계산
                        다른 입력은 수동 가정, 만료하면 계산 보류

별도 예시 선택 → EXAMPLE 출처 (SDK 실패 시 자동 실행되지 않음)
새 차량 조회값 → saved state / PC 상황실 / 디스크 / 실제 기관 전송 없음
긴급 요청 → 위 조회·동의의 성공 여부와 독립
```

통신 성공 시각을 센서 측정 시각으로 해석하지 않는다. 조회 API가 오래된 값을 반환했는지 판별할 센서 타임스탬프는 이 계약에서 제공하지 않는다. 수신 후 30초는 **앱이 오래된 조회 결과를 재사용하지 않기 위한 한도**다. 세 값을 동시에 측정한 원자적 스냅샷도 아니며, 각 값마다 수신 시각이 다를 수 있다.

주행 중 실제 CarUX가 상세 조작을 막으면 새 조회·상세 동의 화면도 사용할 수 없다. 현재 차량 관측은 자동 수집·자동 전송 기능이 아니며, 정차 시 허용된 조작 또는 일반 Android 예시에서 이용한다. 주행 중 사용할 사전 동의·최소 정보 요약·갱신 정책은 다음 단계의 OEM UX 검증 대상이다. 상세 제한 중에도 긴급 요청 자체는 계속 가능하다.

운전석 신호는 좌측 첫째 열 영역 조회다. 차량의 실제 운전석 배치·차종 지원 여부는 capability와 차종 테스트가 필요하다. 도어는 범위와 위치 신호를 그대로 표시하며 임의로 탑승자·잠금·구조 가능성을 추정하지 않는다. 에어백 false는 사고 없음이나 탑승자 안전을 의미하지 않는다.

## 공식 SDK 계약과 권한

기존 `ai.pleos.playground:Vehicle:2.3.2` 사용. 신규 런타임 라이브러리는 추가하지 않았다.

| 읽기 | API | 권한 | 해석 |
|---|---|---|---|
| 도어 | `checkDoorPositionCapabilities` → `getCurrentDoorPosition` | CAR_DOORS | 반환 위치 정수·capability 범위 |
| SoC | `checkEvBatteryStateOfChargeCapabilities` → `getEvBatteryStateOfCharge` | CAR_ENERGY | 정수 백분율 0~100 |
| 에어백 | `checkAirbagDeployedCapabilities` → `hasSeatAirbagBeenDeployed` | CAR_SAFETY | 좌측 첫째 열 전개 신호 true/false/null |

[공식 소개](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/intro), [권한 목록](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/vehicle-permission), [공식 2.3.2 배포 소스](https://nexus-playground.pleos.ai/repository/maven-releases/ai/pleos/playground/Vehicle/2.3.2/Vehicle-2.3.2-sources.jar)를 대조했다. sources.jar SHA-256: `62b5dd2c4c0523fd13c2e64040cd775bc89a14ce54f35a37560d0eb4eb3fab40`.

API Reference 개별 페이지는 이번 열람에서 제목 외 본문이 충분히 보이지 않았다. 따라서 단위·nullable·권한은 공식 배포 소스 KDoc와 로컬 AAR public 시그니처로 확인했다. `getEvBatteryCapacity/Level`의 `@hide/@suppress` 계약을 발견해 호출하지 않았다. V2L 지원·출력·용량을 SDK에서 확인했다고 주장하지 않는다. CAR_SAFETY는 문서화된 읽기 권한으로만 추가했으며 CONTROL 권한이나 set API는 사용하지 않는다.

[FusedLocation 소개](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/intro), [위치 데이터 접근](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/location-data-access)은 현재 공개되어 있다. ‘준비 중이라서 못 한다’는 과거 문구를 최신 구현 한계로 재사용하지 않는다. 다음 단계는 권한·사용자 동의·정확도·시각·취소를 갖춘 어댑터 구현이다.

## 재현과 검증 구분

1. minSdk 28 / compile·target 34 / JDK 17, 기존 새 PC 가이드로 빌드한다.
2. 일반 Android: 더보기 → 차량 상태 → 새로 조회. 확인 불가를 표시하고 80% 예시로 바뀌지 않아야 한다.
3. 일반 Android: 일반 상태 예시 → 119 요청 → 차량 상태 → 동의 → 전달. 앱 내 수신값에 예시 출처가 있어야 한다. 철회·앱 이탈·만료로 사라져야 한다.
4. SoC 80% 예시를 EV 계산에서 불러온다. 기본 가정 64kWh·보존30%·효율85%·200W에서 27.20kWh. 신호 변화 예시15%에서는 이용가능량0.00kWh. 30초 뒤 계산이 보류되어야 한다.
5. 정상 Pleos 환경: 실제 SDK 조회 후 Virtual Console에서 도어 값을 변경하고 새로 조회/5초 확인한다. SDK 값과 앱 값, 출처, 수신 시각을 함께 기록한다. SoC/에어백 변경을 Console이 제공하지 않으면 해당 주입 검사는 미수행으로 남긴다. 임의 endpoint를 만들지 않는다.
6. 실제 CarUX: P → D/속도 변화 → P 시 상세 제한과 119 접근을 검증한다. 수동 역할 선택이나 추가 제한 토글 결과를 실제 콜백 검증으로 대신하지 않는다.

네이티브 회귀 스크립트: `scripts/verify-vehicle-context.py`, 기존 전체 UI·화면 크기 검사도 v16 지원. 테스트 helper는 의료정보의 FLAG_SECURE를 유지하며 PIN을 입력하거나 저장 정보를 지우지 않는다.

### 이번 Pleos 검증의 제한

전용 AVD `LifeLink119_UI_20261107`을 새로 부팅했으나 지속적인 정상 부팅을 확인하지 못했다. `sys.boot_completed`가 비어 있고 boot animation이 계속됐으며, `ai.pleos.hardware.adas`와 `vehicle_ext` vendor 서비스의 SIGABRT 및 Console `bridge_ready=false`를 기록했다. 앱을 설치하거나 차량 신호를 주입하기 전의 환경 문제다. 원인은 확정하지 않았으며 앱 코드 문제 또는 해결 완료로 단정하지 않는다.

이번 작업이 띄운 headless AVD 프로세스와 해당 임시 ADB forward만 종료했다. 등록 AVD·사용자 데이터와 기존 표시 중인 일반 Android 에뮬레이터는 보존했다. 단위 테스트·표준 Android UI 성공과 실제 Pleos SDK 종단 간 검증 성공을 분리한다. 로컬 증거: `verification/vehicle-context-v16/pleos-validation.json`, `pleos-crash.txt`, `references/initial-console-state.json`.

## PT에서 설명할 수 있어야 할 답변

- **왜 차량 앱인가?** 차 안에서 긴급 요청과 상담을 시작하고, 사용자가 차량에서 확인한 상태를 골라 같은 요청에 덧붙인다. 단순 휴대전화 신고 버튼을 차량 화면에 옮기는 데서 나아간다. 평소에는 가족 정보 관리와 상담으로 재방문할 이유를 제공한다.
- **SDK를 어디에 썼나?** 세 신호를 읽고 capability/오류/시각을 검증한 뒤 전달·전력 계산의 입력으로 사용한다. SDK 개수가 성과 지표는 아니다.
- **왜 자동 신고하지 않나?** 도어/에어백 신호만으로 사람의 의료 상태를 알 수 없다. 필요할 때 즉시 요청하고, 조회 실패도 요청을 막지 않는다.
- **실제와 모의의 경계는?** SDK 조회 코드는 실제 API. 예시 데이터는 별도 출처. 상황실·기관 연락·영상·위치·내비·음성은 기존 모의 기능. 현재 Pleos 실데이터 회귀는 환경 문제로 미완료다.
- **저장·외부 전송은?** 새 차량 관측값은 메모리에서만 이용하고 PC 게시/복원 JSON에는 넣지 않는다. 실제 기관 전송·장기 기록은 별도 운영·동의 설계가 필요하다.
- **다음 우선순위는?** 정상 Pleos 환경에서 SDK→앱 반응을 먼저 입증한다. 이어 위치 어댑터 → 목적지 확인형 내비 → 공개 음성 API 통합. 빌트인캠·디지털키·기관 시스템·외부 등화 제어는 공개 계약·제휴 범위를 확인한 뒤 진행한다.
